三个引擎均在数据库中保存请求限速信息和带版本的会话授权。

## 电子邮件 OTP

当电子邮件不对应于启用的帐户时，登录会返回 403 以 `ACCESS_NOT_ENABLED`，不会发送 OTP 也不会创建用户。界面保留表单并显示警告以检查地址或请求访问。对于不存在、待处理、已暂停或已禁用的帐户，使用相同的消息，不会透露其具体状态。这种政策是为了指导人员，允许区分启用的帐户和没有访问权限的帐户；取代了之前登录的统一响应。IP 和电子邮件的限制仍然保留。注册保持其统一的响应和模式控制。合格的发送通过 `waitUntil` 完成。适配器使用在 `MAIL_PROVIDER` 中配置的提供程序：D1 上的 Cloudflare Email Sending、Worker 和 Node 上的 Resend，或开发用本地邮箱。选择在 `services/mail.ts` 中实现。

代码为六位数字，有效期为五分钟，Better Auth 以哈希值存储。每个 OTP 限制五次尝试，每个电子邮件每十五分钟限制十次验证，每分钟每个电子邮件限制一次发送。此外，每个 IP 地址每十五分钟限制二十次请求，并且有身份验证提供程序的限制。限制存储在 D1 中，节流密钥以 SHA-256 存储。日志中不打印 OTP 或令牌。

`/access/verify` 明确区分登录和注册。登录使用 `disableSignUp:true`，要求已经存在的活动帐户，不会授予对待处理或已暂停的帐户的访问权限。已使用或已过期的 OTP 不会再生成会话。

## Google OAuth

仅当 `GOOGLE_ENABLED="true"` 和两个秘密都存在时才启用。要求 `email_verified` 从 Google 配置文件中获取，并禁用从 OAuth 创建用户。结果通过与电子邮件 OTP相同的状态、会话、权限和 MFA 阻塞。回调：`https://app.example.test/api/auth/callback/google`。在 Google Cloud 中注册该 URI，并配置同意屏幕。此流程在配置凭据后需要外部测试。

## 会话和来源

会话持续八小时，并在 D1 中无 cookie 缓存检查。需要 MFA 时，会话在验证后将带版本的授权快照保存到 D1。每次受保护的操作都检查会话及其版本。有效快照直接提供权限。若面板在写入前收到 `409 authorization_changed`，会更新上下文并为同一用户重试一次。 生产环境中的 HttpOnly、SameSite=Lax 和 Secure cookie。每个 mutation 都需要 `Origin` 等于 `APP_URL`，JSON 和最多 16 KiB 的正文。HTTPS 请求在 localhost 之外是必需的。没有开放的 CORS，也没有在 localStorage 中存储令牌；仅主题和菜单收缩的视觉首选项存储在那里。

网关仅公开 Better Auth 公共处理程序的 Google 路由和注销路由。OTP 方法、代码检查、MFA 和注册不能从服务器策略外部调用。包含令牌的 Better Auth 响应正文不会传递给前端：仅传播其 cookie 和严格必要的数据。

包括安全头和CSP。CSP支持Astro水合和视觉令牌所需的内联脚本/样式；不支持来自Turnstile以外的网站的对象或框架。如果一个派生删除内联脚本，可以使用哈希/nonce加强它。

## 在授权之前渲染管理界面

八个管理文档在没有面板视觉结构的情况下生成。React的初始输出也是空的：在收到私人授权响应之前，不会挂载菜单、头部、视图标题、表单、会话通知或加载指示器。待处理的重定向保留该空输出。电子邮件更改的确认结果作为单独的公共收据显示，因为该操作关闭会话；不会重新挂载面板。这是静态容器的表示更正；私人数据已经通过API受到保护。它不替换其身份验证，也不添加读数。

在加载未确认访问的视图时，403和503错误仅显示公共消息和恢复选项，而不显示面板。在将页面保存到BFCache时，其结构将以同步方式隐藏，并关闭对话框，以便在重新验证期间快照不会再次绘制它。只有授权响应才能再次显示它。

## 由于会话丢失返回登录界面

一个 401 在面板的读取或操作中会使其呈现缓存失效，中止待处理的读取，并在用 `/login/` 替换 URL 之前清除私人数据、QR、种子和临时代码。成功的退出登录使用相同的清除和替换导航。重新打开已关闭会话的管理链接将自动遵循此流程。

从 BFCache 中恢复文档需要从服务器读取当前数据，即使之前的视觉缓存仍然有效。检查 `pageshow` 中的 `persisted` 标志：正常加载和内部导航不会收到额外的查询。由于权限不足导致的 403 不会转为退出登录；`MFA_REQUIRED` 代码将指向 MFA 挑战，而 `RECENT_AUTH_REQUIRED` 将保留最近的身份流程。503 失败也不被解释为会话关闭。目标是固定本地路由。API 将继续以 JSON 格式响应 401/403，无论 HTTP 重定向都会破坏客户端或隐藏错误。

## 自愿 MFA

配置文件 → 安全使用官方的 Two Factor 插件 `allowPasswordless:true`。没有基于电子邮件的第二因素。激活接受在应用程序内的会话期间少于五分钟的输入或确认电子邮件。它生成一个加密的密钥并在激活第二因素之前确认 TOTP。QR 代码是在浏览器中生成的，不会将密钥发送给第三方。相同的配置密钥可以通过单击复制，并可以作为 TOTP 手动加载到身份验证应用程序中。界面在关闭对话框或完成激活后会从其状态中删除 QR 代码和配置密钥。

五分钟的时效性是从创建会话的登录开始计算的，而不是从最后一次活动开始计算的。一般会话仍然持续八小时。除了高级MFA，它支持下面描述的屏幕确认，如果一个敏感操作超过了这个时限，API将返回403并带有`RECENT_AUTH_REQUIRED`；接口将解释原因并提供在`/login/?reauth=1`中确认身份的选项。将请求新的OTP和第二因素（当适用时），并返回到`/admin/security/`。对于个人资料更改，使用`/login/?reauth=profile`，并返回到`/admin/profile/`。目标是从一个固定的列表中选择的：不接受外部回调URL，也不删除最近的第一因素检查。敏感操作在返回时不会自动执行。

插件不会在安装版本中自动拦截所有无密码方法。TBA保留一个与会话、用户及其MFA版本相关的`assurance`表。所有私有API都拒绝一个没有完成第二因素的会话。电子邮件OTP和OAuth首先产生一个待处理的会话，该会话受到该屏障的限制。更改React中的状态或直接调用API不能绕过这一限制。

网关为每个用户每五分钟添加五次第二因素尝试的预算，即使Better Auth收到一个经过第一因素认证的会话。敏感更改需要最近的第一因素和新的TOTP确认或恢复代码。

## 可信设备

安全性中的撤销在应用程序中使用TOTP或新恢复代码确认，且具有五次尝试的限制。它不需要返回到登录界面，因为它需要有效的会话、完成的MFA和第二个因素的新验证。在删除所有可信设备并增加MFA版本后，仅重置刚刚确认代码的会话验证。其他会话必须再次完成MFA。MFA保持活动状态，不会生成新的可信设备。MFA的禁用和其他敏感操作保持其要求。

插件的官方模式 `trustDevice` 本身不能满足此版本所有无密码流程的验证。因此，使用Web Crypto生成的256位随机令牌，存储在HttpOnly、Secure和SameSite=Strict的cookie中。在D1中，只存储令牌的哈希值、用户、MFA版本和绝对过期时间（三十天）。不依赖IP或User-Agent。

可信性仅在验证第二个因素并且通过明确选择之后创建。复选框出现在邮件OTP、验证器和恢复步骤中，并在更改方法或重新发送邮件时保留选择。在OTP期间的选择仅表示MFA步骤的首选项：它本身不会创建可信性，也不会影响没有MFA的帐户。它永远不会替换第一个因素，也不会自动更新。撤销可信性或禁用MFA会删除令牌并增加MFA版本。撤销会话或暂停用户会切断现有的访问权限。在localhost中，省略Secure和前缀 `__Host-` 以允许HTTP开发。

## 恢复

在 HTTPS 中撤销可信设备时，会删除具有适当安全属性的 cookie。禁用 MFA 会撤销信任和会话，按照本指南中描述的规则进行。

十个代码通过 Better Auth 进行加密。在生成时显示，每个代码只能使用一次，总是在第一个因素之后。重新生成会使之前的代码失效。UI 允许复制代码或将其下载到一个名为 `.txt` 的文件中，该文件通过 Blob 在本地生成。该文件包括私有存储说明，并提醒用户电子邮件仍然是必要的。用户必须自行保存该文件；应用程序会撤销临时 URL 并不将其发送到任何服务器。UI 在关闭代码显示时会从内存中删除代码；代码不会在浏览器中持久化。摄像头、短信和第二个电子邮件的权限是不必要的。

## RBAC 和审计

默认拒绝访问。每次私有请求都会校验活动会话和全局授权版本。权限来自带版本的会话快照。快照过期时，服务器重新读取角色并重建快照。管理操作会校验端点权限及管理员身份。撤销会话需要 `users.edit`。触发器保护最后一位活动管理员。

审计记录包括执行者、操作、资源、结果和日期。审计不记录请求体、秘密、代码或令牌。保留期应由应用程序定义；应使用显式任务根据需要计划清理会话、验证、节流、过期信任和审计。第一版本不安装 cron 作业或额外资源。

## 权限和活动呈现

权限和事件的标识符保存在服务器和数据库中。面板会按所选语言翻译标签。新角色获得唯一标识符，现有角色保留原标识符。

审计端点仍然需要 `audit.read` 并通过读取连接来解析关联的用户邮箱或角色名称。如果资源不再存在，则显示一个中立标签。资源描述受影响的元素（会话、第二因素、恢复、个人资料或信任），而不是重复演员的邮箱。在管理操作中，保留受影响的其他人的名称，或如果没有名称，则保留其邮箱；角色和配置显示其可读名称。名称通过现有的读取连接来解析，而不修改事件。原始引用在D1中保持以便跟踪；审计接口不在可展开的详细信息中显示技术代码或标识符。历史记录不会被修改或重写。

选择器使用带有弹出式选项的组合框并保留一个隐藏的 `select` 原生代码以序列化和验证表单。菜单根据可用空间进行定位，而不会被对话框裁剪。允许使用箭头、Home/End、Enter、Escape和Tab进行选择；单击外部、调整大小或移动容器时会关闭。必填字段会聚焦选择器并显示验证消息。没有添加依赖项。自动完成尊重明暗主题的颜色。

## 更改访问邮箱

该配置文件通过 Better Auth 的 Email OTP 插件提供一个指导流程：`POST /api/private/profile/email/request` 将代码发送到新地址，`POST /api/private/profile/email/confirm` 验证并应用更改。两者都需要活动会话，MFA 完成（当适用时），以及不超过五分钟的第一个因素。确认还需要 Authenticator 的新代码或如果帐户具有 MFA 的恢复代码，即使使用可信设备。API 在请求电子邮件时报告 `mfaRequired`，并在使用电子邮件的 OTP 之前拒绝没有第二个因素的确认，使用 `MFA_CONFIRMATION_REQUIRED`。源、JSON、大小和频率的控制保持不变。插件的原始端点仍然被网关阻塞。

使用与用户和新地址关联的带有哈希的 OTP，有效期为五分钟，最大尝试次数为五次。已经使用的地址不会收到代码，也不会替换其他帐户。当前地址在完成验证之前仍然有效。没有手动将任何电子邮件标记为已验证：插件的官方操作仅在验证 OTP 后执行。

Better Auth 验证并消耗邮件验证码。持久化层以原子方式更新用户、增加 MFA 版本、撤销设备和会话并写入审计记录。D1 使用批处理，SQLite 和 PostgreSQL 使用事务。写入失败时请重新请求验证码。

一旦确认该批次，后续准备 Better Auth 响应时发生的故障不会被报告为更改失败。无需发出替换 cookie，因为会话已经被撤销。通过 `waitUntil` 发送到之前地址的通知是在批处理之外发送的；其故障被单独记录，并不会影响更改的成功。错误诊断仅记录阶段、方法和路由标签，而不记录电子邮件、OTP、MFA、cookie 或请求正文。人员必须使用新电子邮件和 MFA 重新登录。保留用户 ID、角色、状态、TOTP 密钥和剩余的恢复代码。如果使用其中一个来确认更改，则会像任何验证一样消费。审计记录事件和用户 ID，而不记录代码或请求正文。无需迁移或新表。

保留基础用户、申请和审计列表，使用有限分页和服务端权限。高级表格引擎及 Excel 导出不属于基础模板，各项目可按需实现。参阅[模板范围](template-scope.md)。

### 在应用程序内激活 MFA 的电子邮件验证

当登录时间超过五分钟时，`enroll` 和 `confirm` 响应 `MFA_ENROLL_CONFIRMATION_REQUIRED`。接口通过 `/api/private/security/enroll/email` 将代码发送到已验证的用户的电子邮件地址，通过 `/api/private/security/enroll/email/confirm` 确认代码，然后继续进行 QR 码验证。不会重定向到登录页面，也不会更改 cookie、会话过期时间或会话权限。过期或已撤销的会话仍然响应 401。

六位数字的加密代码以哈希形式存储，使用应用程序密钥和会话 ID，存储在现有的验证表中。代码在五分钟后过期，允许五次尝试，只能通过条件更新一次消费。每个用户每分钟只能发送一次代码。所产生的授权仅在五分钟内有效，仅用于在该会话中启动和确认 MFA 激活；不替换 TOTP 激活，也不允许更改电子邮件、停用、恢复或撤销。完成 MFA 激活后，授权将被删除。不创建表格、迁移或服务。
