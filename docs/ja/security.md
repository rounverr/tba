3 種類のエンジンで、リクエスト制限とバージョン付きセッション認可をデータベースに保存します。

## Email OTP

入力情報は、有効なアカウントに該当しない場合、`ACCESS_NOT_ENABLED` で 403 エラーを返し、OTP を送信したりユーザーを作成したりしません。インターフェースはフォームを保持し、住所を確認するかアクセスを要求するように警告を表示します。存在しないアカウント、保留中のアカウント、停止されたアカウント、または無効なアカウントについても、同じメッセージが使用され、その具体的な状態は公開されません。このポリシーは、ユーザーを導くために要求され、有効なアカウントとアクセス権のないアカウントを区別することを可能にします。以前のログインの統一されたレスポンスに代わるものです。IP による制限とメールによる制限は保持されます。登録は、統一されたレスポンスとモードの制御を保持します。`waitUntil` を使用して、適切な送信を完了します。アダプターは、`MAIL_PROVIDER` に構成されたプロバイダーを使用します: ステージングでは Cloudflare Email Sending、代替として HTTP トランスポート、テストではローカル メール。選択は `services/mail.ts` に実装されています。

コードは6桁で、5分で期限切れになり、Better Authはハッシュで保存します。OTPごとに5回の試行、15分ごとに10回のメール検証、1分ごとに1回のメール送信が制限されます。また、IPごとに15分ごとに20回のリクエストが制限され、認証プロバイダーの制限もあります。制限はD1に保存され、スロットルキーはSHA-256で保存されます。ログにはOTPやトークンは印刷されません。

`/access/verify` は明示的にログインと登録を区別しています。ログインでは `disableSignUp:true` を使用し、既存のアクティブなアカウントが必要であり、保留中または停止されたアカウントへのアクセスは許可されません。使用済みまたは期限切れのOTPは再度セッションを生成しません。

## Google OAuth

`GOOGLE_ENABLED="true"` が有効で、両方のシークレットが存在する場合のみ有効になります。Googleプロファイルから `email_verified` が必要であり、OAuthからユーザーの作成は無効になります。結果は、Email OTPと同じ状態、セッション、権限、MFAのバリアを通過します。コールバック: `https://app.example.test/api/auth/callback/google` 。Google CloudにこのURIを登録し、同意画面を設定します。このフローでは、資格情報を設定した後、外部の実際のテストが必要です。

## セッションと起源

セッションは8時間続き、D1でCookieのキャッシュなしでチェックされる。MFA が必要な場合は完了後に、セッションがバージョン付きの認可スナップショットを データベースに保存します。保護された操作ごとにセッションとバージョンを確認します。有効なスナップショットから権限を取得します。書き込み前に `409 authorization_changed` が返った場合、パネルは状態を更新し、同じユーザーで一度だけ再試行します。 プロダクションでは、HttpOnly、SameSite=Lax、SecureのCookieを使用する。各ミューテーションでは、`Origin` が `APP_URL` に等しいJSONと、最大16 KiBのボディを必要とする。ローカルホスト以外では、HTTPSリクエストが必須である。CORSはオープンしておらず、localStorageにはトークンは保存されず、テーマとメニューコントラクトの視覚的な設定のみが保存される。

ゲートウェイは、Better AuthのパブリックハンドラーのGoogleとログアウトのルートのみを公開しています。OTP、コードの検査、MFA、サインアップなどのメソッドは、サーバーのポリシー外から呼び出すことはできません。Better Authのトークンを含むレスポンスボディはフロントエンドに渡されません。クッキーと厳密に必要なデータのみが伝播されます。

セキュリティヘッダーとCSPが含まれています。CSPは、Astroの水和と視覚トークンに必要なインラインスクリプト/スタイルを許可します。Turnstile以外のサイトのオブジェクトやフレームは許可されません。インラインスクリプトを削除する派生型は、ハッシュ/ノンスを使用して強化できます。

## - 認証前に管理レンダリングを行う

8つの管理文書は、パネルの視覚的な構造なしで生成されます。Reactの初期出力も空です。メニュー、ヘッダー、ビューのタイトル、フォーム、セッションの通知、またはロードインジケーターは、認可されたプライベート応答を受信する前にマウントされません。保留中のリダイレクトは、その空の出力を保持します。メールの変更の確認結果は、セッションを閉じるため、パネルを再マウントせずに、別のパブリックレシートとして表示されます。これは、静的コンテナーの表示の修正です。プライベートデータはすでにAPIによって保護されていました。認証を置き換えるものでも、読み取りを追加するものでもありません。

アクセスが確認されていないビューの読み込み時に発生する403の拒否と503の障害は、パネルなしで、パブリックメッセージと回復オプションのみを表示します。BFCacheにページを保存すると、その構造が同期的に隠され、ダイアログが閉じられ、インスタントが再検証中にそれを再描画しないようにします。認可された応答のみがそれを再表示します。

## ログインへの戻り - セッションの喪失

401がパネル読み取りまたはアクションで発生すると、表示キャッシュが無効になり、保留中の読み取りが中止され、QR、シード、トランザクショナルコードなどのプライベートデータがクリアされた後、URLが`/login/`に置き換えられます。ログアウトの成功も同じクリーンアップとナビゲーション置き換えを使用します。管理リンクをセッション終了後に再度開くと、このフローが自動的に実行されます。

BFCacheからのドキュメントの復元には、サーバーからの最新の読み取りが必要です。つまり、以前のビジュアルキャッシュがまだ有効であってもです。`pageshow`の`persisted`インジケーターがチェックされます。通常の読み込みと内部ナビゲーションは追加のクエリを受け取りません。許可がない場合の403はログアウトにはなりません。`MFA_REQUIRED`コードはMFAチャレンジに導き、`RECENT_AUTH_REQUIRED`は最近のアイデンティティフローを保持します。503の失敗もセッション終了として解釈されません。宛先はローカルに固定されたルートです。APIはJSON 401/403に応答し続け、クライアントを破壊したりエラーを隠したりするHTTPリダイレクトはありません。

## 任意のMFA

プロフィール → セキュリティは、`allowPasswordless:true` で公式の Two Factor プラグインを使用します。メールによる 2 要素認証はありません。有効化では、5 分未満の入力またはアプリ内でのメール確認 (現在のセッションにリンク) が受け入れられます。暗号化されたシークレットを生成し、2 要素認証を有効化する前に TOTP を確認します。QR コードはブラウザで生成され、シークレットは第三者に送信されません。同じ構成キーはクリック時にコピーされ、認証アプリケーションで TOTP として手動でロードできます。インターフェイスは、ダイアログを閉じたり、有効化を完了したりすると、QR コードと構成キーをその状態から削除します。

5分間の経過時間は、セッションを作成した入力から計算され、最後の活動からではありません。一般的なセッションは8時間間続きます。MFAの登録を除き、下記に記載されている画面での確認を許可しますが、もし機密性の高い操作がその期間を超えた場合、APIは403を返し、`RECENT_AUTH_REQUIRED`で応答します。インターフェースは原因を説明し、`/login/?reauth=1`で身分を確認することを提案します。新しいOTPと2要素認証が必要な場合にそれらを要求し、`/admin/security/`に戻ります。プロフィールの変更には`/login/?reauth=profile`を使用し、`/admin/profile/`に戻ります。送信先は固定リストから選択され、外部のURLを返すことはできず、最近の最初の要素の確認は削除されません。機密性の高い操作は、戻ったときに自動的に実行されません。

プラグインは自動的にインストールされたバージョンのすべてのパスワードレスメソッドを傍受しません。TBAは、セッション、ユーザー、およびMFAのバージョンにリンクされた`assurance`テーブルを保持しています。すべてのプライベートAPIは、2要素認証を完了していないセッションを拒否します。Email OTPとOAuthは、最初にそのバリアの保留中のセッションを生成します。Reactで状態を変更したり、直接APIを呼び出したりしても、それを回避することはできません。

ゲートウェイは、Better Authが最初の要素の認証されたセッションを受信した場合でも、ユーザーごとに5分間で2要素認証の試行を5回まで追加します。機密情報の変更には、最近の最初の要素と新しいTOTPの確認または復旧コードが必要です。

## 信頼できるデバイス

セキュリティからの撤回は、TOTPまたは新しい回復コードと同じ5回の試行制限で、アプリ内で確認されます。ログインへの復帰は、入力の古さのために要求されません。有効なセッション、MFAの完了、および2要素目の新しい検証が要求されます。すべての信頼できるデバイスを削除し、MFAのバージョンを増分した後、コードを確認したばかりのセッションの検証のみがリセットされます。他のセッションは、MFAをもう一度完了する必要があります。MFAは有効なままです。また、新しい信頼できるデバイスは生成されません。MFAの無効化およびその他の機密性の高い操作は、要件を保持します。

プラグインの公式モード `trustDevice` は、単独でこのバージョンのパスワードレスフローのすべての検証を満たしません。したがって、Web Cryptoで生成された256ビットのランダムトークンが使用され、HttpOnly、Secure、およびSameSite=StrictのCookieに保存されます。D1では、トークンのハッシュ、ユーザー、MFAのバージョン、および30日間の絶対有効期限のみが保存されます。IPまたはUser-Agentは信頼されません。

信頼は、2要素の検証後にのみ作成され、明示的な選択によってのみ行われます。チェックボックスは、OTPメールの手順、Authenticator、および回復手順に表示され、方法の変更やメールの再送信時に選択を保持します。OTP中の選択は、MFAステップに対する好みを表すのみであり、信頼を自ら作成したり、MFAのないアカウントに影響を与えたりすることはありません。最初の要素を置き換えることも自動的に更新されることもありません。信頼の撤回またはMFAの無効化により、トークンが削除され、MFAのバージョンが増分されます。セッションの撤回またはユーザーの停止により、既存のアクセスが切断されます。localhostでは、Secureが省略され、`__Host-`のプレフィックスが許可されるため、HTTP開発が可能になります。

## 回復

HTTPSでの信頼できるデバイスの撤回時に、適切なセキュリティ属性を持つCookieが削除されます。MFAの無効化により、信頼とセッションがこのガイドに記載されているルールに従って撤回されます。

ローカルで生成されたBetter Authを使用して10個のコードが暗号化されます。これらは生成時に表示され、各コードは1回だけ使用でき、常に最初の要素の後で使用されます。再生成すると以前のコードは無効になります。UIでは、コードをコピーしたり、`.txt`というファイルにダウンロードしたりできます。このファイルはBlobを使用してローカルで生成され、プライベートストレージの指示と、メールがまだ必要であることを記載しています。ユーザーは自分でこのファイルを保存する必要があります。アプリケーションは一時的なURLを取り消し、サーバーに送信しません。UIは、表示を閉じるとコードをメモリから削除します。ブラウザには保持されません。カメラ、SMS、セカンドメールの許可は必要ありません。

## RBACと監査

アクセスは既定で拒否されます。非公開 API への各リクエストで、有効なセッションとシステム全体の認可バージョンを検証します。権限はバージョン付きのセッションスナップショットから取得します。古い場合はサーバーがロールを読み直して再構築します。管理操作では API の権限と管理者資格を確認します。セッションの失効には `users.edit` が必要です。最後の有効な管理者はトリガーで保護されます。

監査はアクター、行動、リソース、結果、日付を保存します。要求本文、シークレット、コード、トークンは保存しません。保持期間はアプリケーションごとに定義する必要があります。セッションのクリーンアッププログラム、チェック、スロットル、信頼の失効、および監査を含むタスクを明示的に実行して、必要に応じて実行する必要があります。最初のバージョンは、cronジョブまたは追加のリソースをインストールしません。

## 権限と活動の表示

権限とイベントの識別子はサーバーとデータベースに保存されます。画面では選択した言語のラベルが使われます。新しいロールには固有の識別子が割り当てられ、既存のロールは識別子を維持します。

監査エンドポイントは、`audit.read` を要求し続け、読み取りジョインを介してユーザーのメールアドレスまたは関連付けられたロール名を解決します。リソースが存在しない場合は、中立的なラベルが表示されます。リソースは、影響を受けた要素 (セッション、2 番目の要素、回復、プロファイル、または信頼) を説明し、アクターのメールアドレスを繰り返すのではなく、アクティブな管理アクションでは、影響を受けた他の人の名前または名前がない場合はメールアドレスを保持します。ロールと設定は、読み取り可能な名前を表示します。名前は、既存の読み取りジョインを介して解決され、イベントは変更されません。オリジナルの参照は、トレーサビリティのために D1 に保持されます。監査インターフェイスは、詳細を展開する領域で技術的なコードや識別子を表示しません。履歴は変更または書き換えられません。

セレクターは、ポップオーバー内のオプションを持つコンボボックスを使用し、フォームのシリアル化と検証のために、`select` ネイティブの隠し要素を保持します。メニューは、ダイアログによって切り取られることなく、利用可能なスペースに応じて配置されます。矢印、ホーム/エンド、エンターキー、エスケープキー、タブキーによる選択を許可し、コンテナの外側をクリックしたり、サイズを変更したり、移動したりすると閉じます。必須フィールドはセレクターにフォーカスし、検証メッセージを表示します。依存関係は追加されていません。オートコンプリートは、ライトテーマまたはダークテーマの色を尊重しています。

## アクセスのメールアドレスの変更

プロファイルは、Better AuthのEmail OTPプラグインを介したガイド付きフローを提供します: `POST /api/private/profile/email/request` は新しいアドレスにコードを送信し、`POST /api/private/profile/email/confirm` は変更を確認して適用します。両方ともアクティブなセッション、MFAが完了している場合のMFA、5分未満の最初の要素を必要とします。確認には、MFAが設定されている場合、Authenticatorまたは回復の新しいコードも必要です。APIは、メールを要求する際に `mfaRequired` を通知し、2要素認証なしで確認を拒否し、メールのOTPを消費する前に `MFA_CONFIRMATION_REQUIRED` を返します。元のソース、JSON、サイズ、頻度の制御は保持されます。プラグインの生のエンドポイントは、ゲートウェイによってブロックされたままです。

ハッシュ付きのOTPが使用され、5分間有効で、最大5回の試行が可能であり、ユーザーと新しいアドレスにリンクされています。既に使用されているアドレスにはコードが送信されず、他のアカウントに置き換えられません。現在のアドレスは、検証が完了するまで有効なままです。メールは手動で確認されません。プラグインの公式操作のみが、OTPを検証した後で確認を実行します。

Better Auth はメールコードを検証して消費します。永続化層はユーザー更新、MFA バージョンの更新、端末とセッションの失効、監査記録をアトミックに適用します。D1 はバッチ、SQLite と PostgreSQL はトランザクションを使います。書き込みに失敗した場合は新しいコードを要求してください。

そのバッチが確認されると、Better Auth の応答を準備する際の後の障害は、失敗した変更として報告されません。セッションはすでに取り消されているため、置き換え用の Cookie を発行する必要はありません。前のアドレスへの通知は、`waitUntil` を使用してバッチの外で送信されます。その障害は個別に記録され、変更の成功には影響しません。エラーディアグノストは、フェーズ、メソッド、パスのラベルのみを記録し、メール、OTP、MFA、Cookie、または要求本文は記録しません。ユーザーは新しいメールアドレスと MFA で再度ログインする必要があります。ユーザー ID、ロール、状態、TOTP シークレット、および残りの回復コードは保持されます。変更を確認するために使用される場合、それは通常の検証と同じように消費されます。監査は、イベントとユーザー ID を記録しますが、コードまたは要求本文は記録しません。移行や新しいテーブルは必要ありません。

ユーザー・申請・監査の基本一覧は、制限したページ移動とサーバー権限確認付きで残ります。高度な表機構と Excel 出力は基本テンプレートに含めず、各派生プロジェクトで実装します。[対象範囲](template-scope.md)を参照してください。

### アプリ内で MFA を有効にするためのメール確認

5 分を超えるログインの場合、`enroll` と `confirm` は `MFA_ENROLL_CONFIRMATION_REQUIRED` に応答します。インターフェイスは、認証されたアクターのアドレスに `/api/private/security/enroll/email` を使用してコードを送信し、`/api/private/security/enroll/email/confirm` を使用して確認し、続いて QR コードに進みます。ログインにリダイレクトしたり、Cookie を変更したり、セッションの古さや権限を変更したりすることはありません。期限切れまたは取り消されたセッションは、引き続き 401 に応答します。

6桁の暗号化コードは、ハッシュとしてアプリのシークレットとセッションIDとともに、既存の検証テーブルに保存されます。5分で期限切れになり、5回の試行を許可し、条件付き更新によって1回のみ使用されます。送信は、1分あたり1回のユーザーあたりに制限されます。結果として得られる認証は5分間有効で、セッションでのMFAの開始と確認にのみ使用されます。TOTPのアクティベーションを置き換えたり、メールの変更、無効化、復元、または取り消しを許可したりすることはありません。登録が完了すると削除されます。テーブル、移行、またはサービスは作成されません。
